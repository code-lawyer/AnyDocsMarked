# AnyDocsMarked 优化方向评测报告

- **评测日期**：2026-07-22
- **评测版本**：v1.7.1（`VERSION` / 最近提交 `ddd1b08`）
- **评测范围**：三个子模块（`lawiki` / `makeitdown` / `rag-retriever`）的架构、工程质量与能力边界
- **评测方式**：源码走查 + 结构盘点，不含运行期性能压测

---

## 0. 一句话结论

工程成熟度已达较高水位，**不缺"补窟窿"式优化**。真正的杠杆在于：把设计哲学第 2 条「确定性闸门优先」从**出口**（不编造）延伸到**召回侧**（不漏检）——目前"漏检"这个下限还**不可度量、不可门禁**，这是全仓库最大的单点盲区。

### 已经做得好的（不要动的地基）

- **出口闸门扎实**：`lawiki/skill/lawiki/lint/lint.py` 对锚点逐字存在、`[[]]` 死链、时间线日期顺序、勾稽算术、闭世界越界做确定性校验，退出码非 0 即拦；且 lint 自身有测试锁"抓真错不误报"的边界。

- **规格驱动**：每个较大特性 spec → plan → 实现，全部留档于 `docs/superpowers/`。

### 已核实的"非问题"（避免误报）

- `.venv/` 与 `.rag/` 均已在 `.gitignore` 内（第 11、28 行）。Glob 扫到 `*/.venv/*` 只是工具不遵守 gitignore，**不是**仓库把依赖提交了。

## 2. 优化方向（按杠杆从大到小）

### 方向 A：为「漏检」建立可度量的召回评测集 —— 最高优先级 ★★★★★

**问题**：哲学第 2 条在**出口**做得彻底（`lint answer` 0 违规才放行，保"不编造"这个下限）。但另一个下限——**「漏检」**——目前只靠"三层互补 + wiki×RAG 交叉验证"做**结构性兜底**，没有任何**量化指标**。经全仓库检索确认：**不存在**任何 golden set / `recall@k` / MRR 评测资产。

**后果**：一次检索到底漏没漏，系统自己不知道，CI 也测不出。任何对混合检索的改动（RRF 权重、`min_score`、rerank 策略）在回归时只能靠人工感觉，不敢大改。

**建议**：
1. 建一个小型标注评测集（几十条案件问答：问题 → 应命中的锚点 / 源文件 + 序号）。
2. 在 CI 里跑 `recall@k` / `MRR`，设为可观测指标（先观测、后逐步升为门禁）。
3. 让"漏检"和"编造"一样成为**可度量、可设门禁**的量——这只是把既有的闸门哲学延伸到召回侧，不引入新范式。

**为什么最优先**：它是解锁 A 类之外一切检索算法改动的**地基**。没有它，方向 C 的任何优化都无法安全验证。

---

### 方向 B：OCR 互校的准确率建立金标准 ★★★★

**问题**：双 OCR 互校产出 `quality: suspect` 标记，但**漏标率 / 误标率没有度量**。README 点名的事故场景是"金额/日期错一位"，恰恰最依赖 suspect 标记的召回率。

**建议**：做一个几十页的 OCR 金标准小集，**重点标注数字位、日期位**，度量"该标 suspect 的有没有标出来"。与方向 A 同构：把 makeitdown 的质检下限也变成可度量。

---

### 方向 C：检索质量本身的深水区 ★★★（依赖方向 A 先落地）

有了 A 的评测集兜底，才谈得上安全地改这些：

- **查询改写 / 术语归一**：法律近义词扩展（如"表见代理 / 无权代理 / 无权处分"）。**约束**：用受控同义词表而非模型自由发挥，保持确定性可控（符合哲学第 5 条稳定契约）。
- **命题级 / 条款级分块**：已有结构感知分块 + parent context（`chunk.py`），法律条文可试更细的命题切分，评估对精确召回的影响。

---

### 方向 D：把确定性 lint 推到图谱级一致性 ★★★

现在 lint 校验的是**单点**规则（日期顺序、单笔勾稽算术）。可往图谱级推，且全部是纯确定性规则、天然属于既有前/后闸门体系：

- **金额链条净额勾稽**：多笔往来轧差，而非单点算术校验。
- **法律关系角色冲突检测**：同一当事人在两处角色矛盾（如既是"出借人"又被登记为"借款人"）。
- **跨文件重复识别**：同一判决书扫描两次导致覆盖账本虚高——去重 + 一致性校验。

---

### 方向 E：对外可复核的溯源审计包 ★★

**问题**：当前"可信"是**内部** lint 自证。法律场景的终局是对**第三方 / 法庭可复核**。

**建议**：每次问答可导出一个审计包：`问题 → 检索证据 → 逐字锚点 → 结论链`，独立可验。它是**产物**不是界面，不违背"不做独立界面"，把"可溯源"从内部约束升级为对外资产。

---

### 方向 F：性能 / 规模（当前非瓶颈，预留）★★

LanceDB 后端与增量索引（`delete_source` + `file_stamp`）已具备可扩展性。大案（上千文件）下的瓶颈会是**首次 embedding 建索引耗时**；`docs/superpowers/` 已有 long-task observability spec，届时可加"仅变更文件重嵌入"的并行批处理。**现在不必动**。

---

## 3. 小结与建议排序

| 优先级 | 方向 | 是否需前置 |
|---|---|---|
| ★★★★★ | A. 检索召回评测集 + CI recall 门禁 | 无——立即可做 |
| ★★★★ | B. OCR suspect 金标准小集 | 无 |
| ★★★ | C. 查询改写 / 分块深化 | 依赖 A |
| ★★★ | D. 图谱级一致性 lint | 无 |
| ★★ | E. 对外溯源审计包 | 无 |
| ★★ | F. 大案索引性能 | 规模触发后再做 |

**落地建议**：从**方向 A** 开始。它是唯一一个"解锁其它检索改动"的地基，且与项目既有的"确定性闸门优先"哲学完全同构——不是新增范式，只是把闸门从出口延伸到入口。下一步可产出一份《召回评测集 + CI recall 门禁》的最小实现 spec。
